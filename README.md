# Instrument Technical Support Assistant

A retrieval-augmented technical support assistant for a fictional line of
laboratory instruments (density meters and rheometers). Given a support
ticket — model number, error code or symptom, optional free text — it
retrieves the relevant manual section, drafts a grounded resolution with
citations back to the source documentation, and flags escalation to a human
technician rather than guessing when retrieval support is weak. The project
is built to demonstrate retrieval quality and evaluation rigor: a real
hybrid (BM25 + dense + cross-encoder rerank) retrieval pipeline, a from-scratch
eval harness with a hand-authored ground-truth test set, and a measured,
honestly-reported 3-way ablation rather than a single anecdotal demo.

## Synthetic corpus disclosure

**All product documentation in this repository is synthetic.** The two
fictional instrument families (`DM-` series density meters, `RH-` series
rheometers) sit in the same general product space as real laboratory
instrumentation vendors, but every manual, spec sheet, and application
report is original content generated by an LLM (Gemini) for this project,
then rendered to real PDF/HTML files. Nothing here is scraped, copied, or
adapted from any real vendor's documentation. This keeps the project free
of copyright/ToS concerns while preserving enough domain fidelity —
tables, multi-step procedures, overlapping error codes across models — to
exercise a real ingestion and retrieval pipeline.

## Architecture

The system is split into a **domain-agnostic core** (reusable for any future
corpus and use case) and a **domain layer** (one concrete instance built
now). Full design rationale: [`docs/superpowers/specs/2026-09-12-instrument-support-assistant-design.md`](docs/superpowers/specs/2026-09-12-instrument-support-assistant-design.md).

```
core/
  ingestion/   PDF/HTML parsing + section/procedure-aware chunking
  retrieval/   BM25 + dense embeddings (Chroma) + cross-encoder reranker
  generation/  grounded-answer generation, citation extraction, refusal
  eval/        precision/recall@k, LLM-judged faithfulness, hallucination rate
domains/
  instrument_support/   ticket triage agent for this corpus (the one
                         concrete domain built on top of the generic core)
serving/
  api.py             FastAPI: POST /ticket, POST /ask, GET /health
  streamlit_app.py   deployed UI, embeds the core modules in-process
```

**Ingestion & chunking:** `pdfplumber` (PDF) and `BeautifulSoup` (HTML) both
normalize into `(heading_path, block_type, content)` blocks. Chunks never
straddle two unrelated sections; a table is never split and carries its
heading with it; a numbered procedure only splits at step boundaries.
Every chunk's indexed text is prefixed with its section heading (e.g.
`Error Codes > E-104`) — technical docs pack meaning into structural units,
and a chunk's heading is often the only place the identifier a user actually
searches for (an error code) appears at all.

**Retrieval:** dense embeddings (`sentence-transformers/all-MiniLM-L6-v2`,
local) and BM25 (`rank_bm25`) each retrieve top-20 candidates, fused via
Reciprocal Rank Fusion, then reranked by a cross-encoder
(`cross-encoder/ms-marco-MiniLM-L-6-v2`, local) to the final top-5 sent to
generation. BM25 catches exact model numbers and error codes that dense
embeddings blur; the reranker re-scores the fused candidates jointly with
the query for precision.

**Generation & agent:** retrieved chunks are assembled into a context block
sent to Gemini with a strict grounding prompt — answer only from the
provided excerpts, cite every claim as `[doc_id, section]`, say "insufficient
information" instead of filling gaps from general knowledge.

(The project was originally scoped around Claude Haiku; it moved to the
Gemini API specifically so the full corpus generation and ~240-call eval
ablation could run entirely on a free tier at zero cost, rather than a paid
API — a deliberate cost constraint for a self-funded portfolio project, not
a capability tradeoff. The LLM client is a thin, swappable adapter —
`core/generation/llm_client.GeminiClient` — precisely so this choice isn't
load-bearing.)

The agent's confidence score derives from the reranker's top-chunk score (hard-0 when
the ticket names a model number not present in the corpus at all); below a
threshold, the response states insufficient documentation and recommends
escalation instead of guessing.

## Ablation results

The same 40-item eval set, run three ways: keyword-only (BM25), dense-only,
and hybrid+rerank.

| method | precision@3 | precision@5 | recall@3 | recall@5 | faithfulness | hallucination rate |
| --- | --- | --- | --- | --- | --- | --- |
| bm25_only | 0.208 | 0.140 | 0.375 | 0.425 | 0.650 | 0.000 |
| dense_only | 0.217 | 0.170 | 0.4875 | 0.600 | 0.500 | 0.000 |
| hybrid_rerank | 0.233 | 0.150 | 0.475 | 0.5125 | 0.667 | 0.000 |

(Full precision, generated by [`scripts/run_eval.py`](scripts/run_eval.py), in
[`results.csv`](results.csv) / [`results_table.md`](results_table.md).)

## What fails and why

The aggregate table alone doesn't tell the real story — breaking the eval
set down by the ground-truth `tag` each item was authored with does:

| tag (n) | bm25 p@5 / r@5 | dense p@5 / r@5 | hybrid+rerank p@5 / r@5 |
| --- | --- | --- | --- |
| `collision` (2) | 0.00 / 0.00 | 0.10 / 0.50 | **0.20 / 1.00** |
| `symptom_two_hop` (6) | 0.47 / 0.67 | **0.50 / 0.83** | 0.43 / 0.58 |
| `straightforward` (22) | 0.13 / 0.59 | **0.16 / 0.82** | 0.14 / 0.68 |

- **`collision` — hybrid+rerank's actual reason to exist.** These items
  probe the deliberately engineered retrieval-hard case: the same error
  code (`E-104`) means a different failure mode on the DM-5400 (air bubble
  in the density cell) than on the DM-8200 (a different fault entirely).
  BM25-only misses both items completely — its top hits are generic
  troubleshooting tables from unrelated models. Dense-only finds only one
  of the two, and for the DM-5400 query it retrieves the *DM-8200's*
  `Error Codes > E-104` section instead of the DM-5400's — embedding
  similarity alone can't reliably separate two near-identical sections that
  differ only in which model they belong to. Hybrid+rerank is the only
  configuration that gets both right, because the cross-encoder scores the
  full RRF-fused candidate set (including the correct model-specific chunk)
  jointly against the query text.
- **`symptom_two_hop` and `straightforward` — dense-only actually edges
  ahead.** These make up the bulk of the set (28/40 non-out-of-scope items).
  Here, plain dense retrieval outperforms hybrid+rerank on both
  precision@5 and recall@5. Investigated whether this was a pipeline bug
  (insufficient reranker candidate pool, or the fused set dropping
  candidates) — it isn't: the correct chunk is confirmed present in the
  reranker's full candidate set in every case checked. It reads instead as
  a real property of this specific pretrained cross-encoder: it tends to
  favor longer, narrative "Overview"-style prose over terse spec-sheet or
  procedure text for short factual lookup queries, which costs it a few
  points against dense embeddings on straightforward single-hop questions.
  Net effect: hybrid+rerank trades a small amount of aggregate precision/recall
  on the easy majority of queries for a large, reliable win on the specific
  disambiguation case it was built to solve, plus the best faithfulness
  score of the three (0.667 vs. 0.500 for dense-only) — the model hedges
  and cites correctly more often when the reranker has narrowed the context.
- **Hallucination rate on `out_of_scope` items: 0.000 for all three
  configurations.** All 10 out-of-scope questions (asking about a model or
  feature genuinely absent from the corpus) were correctly refused rather
  than answered by fabrication, regardless of retrieval method — the
  grounding prompt's "insufficient information" instruction held up even
  when retrieval returned only irrelevant chunks.

This is why the ablation is reported as a genuine 3-way comparison rather
than declaring a single winner: the honest finding is that hybrid+rerank's
value is concentrated in the specific disambiguation case it targets, not a
uniform win across every query type on a corpus this small.

## Observability

Every request is logged to a local SQLite file (`observability/db.py`):
latency breakdown, token counts, retrieved chunks and scores, and the final
confidence/escalate decision. `python -m scripts.observability_summary`
prints aggregate stats (p50/p95 latency, token usage, escalation rate).
Cost is $0 — corpus generation, evaluation, and serving all run on the
Gemini API's free tier.

## Production considerations

This project's stack (Chroma, local sentence-transformers, SQLite, Streamlit
Cloud) is sized for a synthetic ~80-chunk corpus at zero cost, not
enterprise scale. It's a deliberately different set of tradeoffs than a
cloud-native deployment would make, not a smaller version of one. If this
pipeline were rebuilt against a real document set on Azure/Databricks:

- **Vector store:** Chroma's file-based persistence is fine for 80 chunks
  committed to git; it isn't a multi-writer, horizontally-scalable store.
  **Azure AI Search** would replace it — native vector + hybrid (BM25)
  search in one service (collapsing this project's separate BM25 index and
  RRF fusion step into the platform), plus access control and scaling this
  project doesn't need to solve itself.
- **Ingestion at scale:** `scripts/build_index.py` parses ~16 documents
  serially, in-process. Thousands of manuals with a real update cadence
  would need a **Databricks** pipeline instead: Spark for parallel
  PDF/HTML parsing and chunking, Delta Lake as the versioned chunk store
  (this project's flat JSONL doesn't handle concurrent writers or
  incremental re-ingestion when a source doc changes), and Databricks
  Workflows to schedule re-indexing rather than a manually-run script.
- **Eval as a tracked artifact, not a file:** `results.csv` is fine for one
  ablation run authored by one person. At scale, eval runs (which retrieval
  config, which model version, which corpus snapshot) belong in **MLflow**
  (Databricks-native) so results are comparable across runs over time
  instead of overwritten by the next `run_eval.py` invocation.
- **Generation model:** swapping Gemini for **Azure OpenAI** is a
  `LLMClient` implementation, not an architecture change — see the note on
  `GeminiClient` above.
- **Secrets & observability:** Streamlit's secrets manager and a local
  SQLite log become **Azure Key Vault** and **Azure Monitor/Application
  Insights** respectively, for centralized secret rotation and request
  tracing across more than one process.

## Setup

```bash
pip install -e ".[dev]"
python -m corpus.generate_corpus     # generate synthetic corpus content (Gemini)
python -m corpus.render_corpus       # render to real PDF/HTML files
python -m scripts.build_index        # parse, chunk, and index the corpus
python -m scripts.run_eval           # run the 3-way retrieval ablation
streamlit run serving/streamlit_app.py
```

`GEMINI_API_KEY` must be set in the environment for corpus generation,
evaluation, and serving (any step that calls the Gemini API).

## Local API (optional)

A standalone FastAPI service is also included for local/non-Streamlit use
(`serving/api.py`): `POST /ticket`, `POST /ask`, `GET /health`. It is not
part of the deployed Streamlit Cloud app, which embeds the core modules
in-process instead of calling this service over the network.
